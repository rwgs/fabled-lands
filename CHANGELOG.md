# Changelog

Changes that consumers of this project need to know about, newest first.

Create this file when the project has consumers who install or upgrade it
independently of its source, including the maintainers themselves on other
machines. A project whose only readers are its own source tree does not need
one, and a changelog nobody updates is worse than none because it misreports
what shipped.

State the audience in one line so entries stay at the right altitude, then
record one entry per user-visible change rather than one per commit. Internal
refactors, test changes, and documentation edits belong in the commit history.

## <Version or date>

- What changed, described by its effect on the consumer rather than by the code
  that changed.
- Any action the consumer must take, such as rerunning an installer, migrating
  data, or updating configuration.
- Removals and breaking changes first, because those are the entries that decide
  whether an upgrade is safe.
